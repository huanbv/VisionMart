# Database Overview

PostgreSQL 16 is the **only** primary OLTP store
([ADR-004](adr/ADR-004-postgresql.md)). Redis is restricted to ephemeral
real-time state ([ADR-010](adr/ADR-010-redis.md)); MinIO / S3 owns
binaries ([ADR-011](adr/ADR-011-minio.md)). No business logic lives in
the database — no stored procedures, no business triggers
([Architecture Contract §2.6](ARCHITECTURE_CONTRACT.md#26-database-rules)).

### Design pillars

| # | Pillar | What it means in practice |
|---|--------|---------------------------|
| 1 | **Multi-tenant by row, not by schema (for v1)** | Every business row carries `organization_id`. Schema-per-tenant remains an option for premium customers. |
| 2 | **Strict per-context ownership** | Each bounded context owns its tables. No SQL `relationship()` crosses module boundaries; FK columns are allowed, navigation goes through repositories. |
| 3 | **UUID primary keys** | Generated by Postgres (`gen_random_uuid()`); safe to expose, easy to shard. |
| 4 | **Audit-friendly by default** | Common mixins for `created_at`, `updated_at`, `is_deleted`, `deleted_at`, `created_by`, `updated_by`. |
| 5 | **Soft delete for business entities; hard delete for transient state** | Orders, customers, products keep history. Sessions, idempotency keys, frame buffers are hard-deleted by TTL. |
| 6 | **Time-series tables partitioned by time** | High-volume tables (AI events, audit, analytics aggregates) use range partitioning so retention is a partition drop. |
| 7 | **JSONB for flexible, low-cardinality attributes; relational for everything queried by predicate** | Attributes, AI configs, audit diffs are JSONB. Anything filtered, joined, or counted is a real column. |
| 8 | **Named constraint convention** | All constraints follow deterministic names (`pk_`, `fk_`, `uq_`, `ix_`, `ck_`) so Alembic diffs are stable. |

### Storage tiering

| Tier | Where | What lives there |
|------|-------|------------------|
| **Hot OLTP** | Postgres primary | All system-of-record data. |
| **Warm read** | Postgres read replica | Reporting / analytics queries; AI dashboard joins. |
| **Ephemeral real-time** | Redis | Active carts mirror, AI track windows, sessions, rate limits, pub/sub. |
| **Binary** | MinIO / S3 | Frames, snapshots, clips, product images, report exports, model artefacts, embeddings. |
| **Cold archive** | S3 Glacier / equivalent | Detection events and audit logs older than the hot-window. |

# Relationships

### One-to-Many (the dominant pattern)

- `Organization → Branch`, `Organization → User`, `Organization → Role`,
  `Organization → Customer`, `Organization → Product`,
  `Organization → Notification`, `Organization → AuditLog`.
- `Branch → Camera`, `Branch → Employee`, `Branch → InventoryItem`,
  `Branch → ShoppingCart`, `Branch → Order`, `Branch → Zone`.
- `Category → Category` (self-reference, parent / children).
- `Category → Product`.
- `Product → InventoryItem`, `Product → ProductMedia`,
  `Product → OrderLine`, `Product → CartLine`.
- `InventoryItem → StockMovement` (append-only history).
- `ShoppingCart → CartLine`; `Order → OrderLine`;
  `Order → Payment`; `Payment → Refund`.
- `Camera → VisionPipeline`; `Camera → TrackingSession`;
  `Camera → Snapshot`.
- `VisionPipeline → ModelRegistration`; `VisionPipeline → AIEvent`.
- `TrackingSession → DetectionResult` (high volume, partitioned).
- `Notification → DeliveryAttempt`.
- `Report → ReportRun`; `Report → ScheduledReport`.

### Many-to-Many (link tables)

- `User ↔ Role` via **`UserRole`** (`granted_at`, `granted_by` audit
  columns).
- `Role ↔ Permission` via **`RolePermission`** (no extra payload).

### Aggregation relationships (lifecycle ties)

- A `CartLine` exists **only inside** a `ShoppingCart` aggregate; deletion
  of the cart deletes its lines (`CASCADE`).
- An `OrderLine` exists **only inside** an `Order` aggregate (`CASCADE`).
- A `StockMovement` is **only meaningful** in the history of an
  `InventoryItem`; deletion of the inventory item is forbidden while
  movements exist (`RESTRICT`).
- A `DeliveryAttempt` belongs to one `Notification` (`CASCADE`).
- A `DetectionResult` belongs to one `TrackingSession` (`CASCADE` on the
  partition).
- A `ModelRegistration` is associated with one `VisionPipeline`
  (`CASCADE`).

### How Branch isolates data

- `Branch.organization_id` is the discriminator linking every branch
  back to its tenant.
- Every operationally-scoped row that pertains to a branch carries
  `branch_id` (and also `organization_id` for fast tenant-only scans).
- Application services receive a principal with the allowed
  `branch_id` set; queries are filtered at the repository layer.

### How Organization groups Branches

- One Organization → many Branches. Branches share the catalog and
  customer base of their organization but not with other organizations.
- Org-wide users (`org_admin`) see all branches of their organization.
- Roles and permissions are organization-scoped.

### How Users belong to Branch or Organization

- A `User` always belongs to **one Organization**.
- A `User` is granted access to **zero, one, or many Branches** via the
  combination of their assigned roles and an explicit `User → Branch`
  assignment table (held inside the Identity context — for
  documentation purposes this is treated as part of `UserRole`'s
  semantics when a role is branch-scoped).
- Org-wide roles (e.g. `super_admin`, `org_admin`) imply access to all
  branches.

### How Orders relate to Cart

- A `ShoppingCart` may be converted to **at most one** `Order`. The
  conversion sets `ShoppingCart.status = CONVERTED` and
  `ShoppingCart.converted_at`, and sets `Order.cart_id` to the source
  cart (nullable, `ON DELETE SET NULL` so cart cleanup never breaks
  order history).
- Lines are **copied** from `CartLine` to `OrderLine` so that the
  immutable order is decoupled from any later cart edits.

### How AI events link to Products and Customers

- `AIEvent` carries optional `product_id` (resolved by the recognition
  step) and optional `customer_id` (resolved only when consent allows).
- Both FKs use `ON DELETE SET NULL` so deleting a product or customer
  does not erase the historical event — the event becomes anonymised.
- `DetectionResult` rows reference the parent `TrackingSession` only;
  they do **not** link to a product or customer directly. The
  AI-business mapping is done in `AIEvent`.

# Multi-Tenant Strategy

### Isolation strategy (v1)

- **Shared schema, row-level discriminator.** Every tenant-scoped table
  carries `organization_id`. There is exactly one Postgres database
  serving all tenants in v1.
- **Branch-level filtering** is layered on top using `branch_id` for the
  subset of tables that are branch-scoped.
- Pure tenant-scoped tables (Catalog, Categories, Roles, Permissions
  membership) carry only `organization_id`.
- Truly cross-tenant tables (Permission catalogue, global SystemSetting
  rows with `organization_id IS NULL`) are explicitly enumerated and
  reviewed.

### Branch-level filtering strategy

- Repositories that wrap branch-scoped tables transparently inject a
  `branch_id IN (:allowed_branch_ids)` predicate based on the current
  principal.
- Cross-branch aggregation is allowed **only** when the principal holds
  an organization-wide permission (`branch.read.all`).
- Background jobs run with an explicit tenant + (optionally) branch
  context taken from the job payload; they cannot silently cross
  boundaries.

### Shared vs isolated data rules

| Data | Visibility |
|------|-----------|
| Organization, Branch | Tenant-only. |
| User, Role, Permission membership | Tenant-only. |
| Permission catalogue | Global (read-only enum-like table). |
| Catalog (Category, Product, ProductMedia) | Tenant-only. |
| Customer, CustomerConsent, FaceEmbeddingRef | Tenant-only; **never** shared across tenants even when the same physical person is the customer. |
| Employee, Camera, Inventory, Cart, Order, Payment | Branch-scoped (and tenant-scoped). |
| AI events, DetectionResult, Snapshot | Camera-scoped → Branch-scoped → Tenant-scoped. |
| Notification | Tenant-scoped, optionally branch-scoped. |
| Analytics aggregates | Tenant-scoped; granular roll-ups are branch-scoped. |
| AuditLog | Tenant-scoped (with nullable `organization_id` for system-level events). |

### Prevention of cross-branch data leakage

Defence in depth:

1. **Application layer** — every request derives `(organization_id,
   allowed_branch_ids)` from the JWT and injects it into application
   services. Clients **cannot** pass tenant/branch IDs as
   query parameters that override scope.
2. **Repository layer** — base repository methods always include the
   scope predicate; raw SQL is reviewed in code review and lint.
3. **Database layer** — `organization_id` is the leading column on
   almost every index, making any forgotten predicate a performance
   cliff (not a correctness one — but the predicate is still required
   by code review).
4. **Negative tests** — the regression suite includes deliberate
   cross-tenant and cross-branch access attempts that must produce 403
   / empty results.
5. **Audit** — every `PermissionDenied` event is recorded; spikes
   trigger investigation.

### Future option

- Premium tenants can be migrated to **schema-per-tenant** or
  **DB-per-tenant** without rewriting business code, because every
  query already includes `organization_id` and there are no implicit
  joins across tenants.

# AI Data Model

> AI data has two regimes: a **low-volume, high-signal** stream of
> domain events the business cares about (cart updates, theft, queue
> alerts, etc.) and a **high-volume, low-signal** stream of per-frame
> detections used for tracking, debugging, and aggregation. They live in
> different tables with different lifecycle rules.

### `VisionPipeline`

- One row per `(camera, pipeline_kind)` combination.
- Holds the **active** `ModelRegistration` reference and the toggles
  derived from `CameraAIConfig`.

### `ModelRegistration`

- Identifies which model version is active for a `VisionPipeline`.
- Carries `model_name`, `model_version`, `model_hash`,
  `backend` (`cpu`|`cuda`|`tensorrt`), evaluation metrics snapshot,
  `activated_at`, `activated_by`.
- Only **one** model registration per pipeline is active at any time.

### `TrackingSession`

- Represents a single shopper/object track lifetime within a single
  camera (and optionally extended via cross-camera re-ID).
- Columns: `id`, `organization_id`, `branch_id`, `camera_id`,
  `track_id` (engine-assigned), `started_at`, `ended_at`,
  `object_class`, `attributes` (JSONB: e.g. demographic estimates),
  `customer_id` (nullable, set only when consented recognition
  occurs).
- Sessions are short-lived (seconds to minutes); long sessions are
  closed and a new one starts.

### `DetectionResult` (high-volume, time-partitioned)

- One row per per-frame detection that we choose to retain (sampled,
  not every frame).
- Columns: `id`, `tracking_session_id`, `camera_id`, `frame_ref`
  (logical pointer — `(camera_id, occurred_at, sequence)`),
  `bbox` (JSONB: `{x, y, w, h}`), `confidence` (decimal),
  `object_class`, `payload` (JSONB for class-specific extras),
  `occurred_at`.
- Partitioned by **monthly range** on `occurred_at`.
- Default retention 30 days; older partitions dropped or moved to
  cold archive.

### `AIEvent` (high-signal, queryable)

- One row per **business-relevant** vision event:
  `ProductPickedUp`, `ShelfBecameEmpty`, `QueueDetected`,
  `TheftDetected`, `CustomerDetected`, etc.
- Columns: `id`, `organization_id`, `branch_id`, `camera_id`,
  `tracking_session_id` (nullable), `event_type`, `payload` (JSONB
  with the event-specific data), `confidence` (decimal),
  `product_id` (nullable FK), `customer_id` (nullable FK),
  `occurred_at`, `correlation_id`.
- Partitioned by **monthly range** on `occurred_at`.
- Default retention 90 days; aggregated into Analytics before purge.

### `Snapshot`

- Metadata for an evidence frame stored in MinIO.
- Columns: `id`, `organization_id`, `branch_id`, `camera_id`,
  `occurred_at`, `object_uri` (MinIO key), `mime_type`, `width`,
  `height`, `purpose` (`incident`, `audit`, `training`,
  `low_confidence`), `linked_ai_event_id` (nullable),
  `linked_audit_log_id` (nullable).
- Snapshots have their own retention policy independent of the AI
  event tables.

### `FaceEmbeddingRef`

- Lives in the Customer context; AI Engine reads it for recognition
  only when the **active consent** check passes (BR-22, BR-23).
- The embedding **vector** is stored in MinIO; this table holds the
  reference (URI, dimension, model version, registered_at).

### Confidence scores and thresholds

- Every AI table carries a `confidence` column (decimal `0..1`).
- Threshold enforcement is **in the AI Engine's rule layer** before
  `AIEvent` is written; lower-confidence detections may be written to
  `DetectionResult` for analytics/debugging but **MUST NOT** trigger
  business actions (BR-25, BR-26).

### Time-series characteristics

- `DetectionResult`, `AIEvent`, `AuditLog`, and the analytics
  aggregates are time-series tables. Their **leading index column** is
  the timestamp; their **physical layout** is range-partitioned by
  time.

# Real-Time Data Model

> Real-time data is **mirrored** in Redis for low-latency reads/writes
> while the **system of record** stays in Postgres. Redis loss must
> degrade performance, never lose business state.

### Active carts

- **Postgres** holds the authoritative `ShoppingCart` + `CartLine`
  rows.
- **Redis** mirrors a flat representation under
  `cart:{branchId}:{cartId}` for ≤ cart TTL.
- Writes flow: `application service → Postgres (commit) → Redis
  (refresh) → pub/sub fan-out`.
- On Redis loss, the next read repopulates from Postgres.

### Live detections / track state

- **Redis only** for the rolling window used by the AI rule engine
  (`ai:track:{cameraId}:{trackId}` with seconds-to-minutes TTL).
- Stable derivatives (`AIEvent`, `TrackingSession` closure) are
  persisted to Postgres.
- **Raw frames** never enter Postgres; they pass through the AI
  Engine's memory or, for evidence, land in MinIO.

### Camera streaming metadata

- `Camera.is_online` and `Camera.last_seen_at` are kept in Postgres
  for durability across restarts.
- A short-lived `cam:health:{cameraId}` key in Redis carries the most
  recent heartbeat for sub-second readers; a Celery / background loop
  reconciles to Postgres at a slower cadence.

### Temporary session data

- **Sessions** are persisted to Postgres (`Session` table) for
  durability and revocation auditing.
- **Token revocation lists** live in Redis (`auth:revoked:{tokenId}`)
  with TTL equal to the token's remaining lifetime — Redis is the
  authoritative store here precisely because the data is naturally
  short-lived.
- **Rate-limit counters** and **idempotency keys** are Redis-only.

### Redis vs PostgreSQL — decision matrix

| Data | Postgres (authoritative) | Redis (mirror / only) | Notes |
|------|--------------------------|------------------------|-------|
| Carts and orders | ✅ | mirror | UI hot path reads from Redis when available. |
| Inventory levels | ✅ | mirror (counts) | Decrements remain transactional in Postgres. |
| Sessions (record) | ✅ | — | Auditable login history. |
| Token revocation | — | ✅ | Naturally TTL'd. |
| Detection raw stream | — | ✅ (window) | Dropped after the rule layer fires. |
| AI events (high-signal) | ✅ | — | Time-partitioned. |
| Pub/sub for WebSocket | — | ✅ | Cross-instance fan-out. |
| Snapshots (binary) | — | — | MinIO; Postgres only holds metadata. |

| `AuditLog` *(partitioned)* | per-partition `(organization_id, occurred_at desc)`; `(resource_type, resource_id)`; `(actor_user_id, occurred_at)`. |
| Analytics aggregates | `(organization_id, branch_id, bucket_start)` per table. |

### Partitioning

- **Monthly range partitioning** for:
  - `DetectionResult` (30 days hot, drop older)
  - `AIEvent` (90 days hot, archive older)
  - `AuditLog` (12 months hot, archive older)
  - All analytics aggregate tables
- Partition maintenance is automated by a Celery Beat job (create next
  partition; drop / archive expired partition).

### Time-series handling

- Time-bucketed aggregates (`*_Aggregate` tables) carry a
  `bucket_start` and `granularity` (`hour`, `day`, `week`).
- Roll-ups are computed by background jobs reading from `AIEvent` and
  `Order`; they are **idempotent** on `(scope, bucket_start,
  granularity)` so re-running is safe.
- Real-time charts read the **most recent partial bucket** from
  Postgres; finished buckets are immutable.

### Hot vs cold data separation

| Tier | Window | Storage |
|------|--------|---------|
| **Hot** | Last 30–90 days | Postgres primary; uncompressed; fully indexed. |
| **Warm** | 90 days–1 year | Postgres detached partitions; reduced indexes. |
| **Cold** | > 1 year (or per regulatory minimum) | Parquet exports in S3 / MinIO; queryable via a future analytics tool. |
| **Archived audit** | per regulatory retention | Append-only S3 bucket with object-lock retention. |

### Connection management

- Application pools the database (per-process pool, modest size).
- Single shared **PgBouncer** in front of Postgres for spiky traffic.
- Read-only analytics workload routed to a **read replica**.

# Audit & Logging

### `AuditLog` structure (conceptual)

| Column | Description |
|--------|-------------|
| `id` | UUID primary key. |
| `organization_id` | Nullable (for system-level events). |
| `occurred_at` | Server timestamp (UTC). |
| `actor_user_id` | Nullable (system actors are recorded by `actor_type`). |
| `actor_type` | `user`, `system`, `service_account`, `ai_engine`. |
| `action` | Verb in past tense (`order.refunded`, `user.role.assigned`). |
| `resource_type` | Domain object class (`Order`, `User`, `Camera`). |
| `resource_id` | Domain object identifier. |
| `old_values` / `new_values` | JSONB diffs (selective columns, no secrets). |
| `correlation_id` | The originating request's `X-Request-ID`. |
| `ip_address`, `user_agent` | For HTTP-originated actions. |
| `metadata` | JSONB for action-specific context. |

- **Append-only**. The table has **no update path**; corrections are
  expressed as a new audit entry.
- Partitioned monthly by `occurred_at`.

### System event logging

- Service-level events (process start/stop, configuration reload,
  scheduled job results) are written to the **structured log stream**
  (JSON) — not to `AuditLog`. Logs are shipped to the central log
  store (Loki / vendor equivalent).
- A subset of high-importance system events (e.g. model deployment,
  consent change) **also** writes an `AuditLog` row.

### User action tracking

- Every privileged HTTP request writes an audit row containing the
  `correlation_id`, principal, action, target, and result.
- Failed authorization (`PermissionDenied`) is always audited, even
  when the request never reached business logic.

### AI event logging

- `AIEvent` (high-signal) is the AI domain's audit-equivalent. It
  carries enough information to reconstruct what the system "saw" and
  why an automated action was taken.
- Per-frame `DetectionResult` rows are **operational** data, not
  audit; they have shorter retention.
- Model deployments, threshold changes, and pipeline enable/disable
  toggles always write an `AuditLog` row.

# Data Lifecycle

### Creation flow

1. Application service validates input and builds the aggregate.
2. The aggregate's invariants are checked **inside the domain**.
3. The repository persists the aggregate in **one transaction**;
   server-generated columns (UUID PK, timestamps) are populated by
   Postgres.
4. Post-commit, the application service publishes any domain events
   via the EventBus.
5. Background side-effects (notifications, cache refresh) happen
   asynchronously.

### Update flow

- Updates always pass through the **aggregate root** — no partial
  updates that bypass invariants.
- `updated_at` is set by the ORM mixin on every save; `updated_by`
  carries the principal.
- For high-contention tables, optimistic locking via a `version`
  column **MAY** be added when measurement justifies it.

### Archival strategy

- Time-series tables are archived at the **partition** level — detach,
  export to Parquet on S3 / MinIO, drop the local partition.
- Business tables (Orders, Customers, Products) use **soft delete**
  (`is_deleted`, `deleted_at`) by default; they are not archived
  unless regulation requires it.
- Periodic **integrity scans** check that archived data is readable
  and that summary counts match the pre-archive snapshot.

### Deletion rules

| Data | Default delete behaviour |
|------|--------------------------|
| Orders, Payments, Refunds, OrderLines | **Never** deleted. Soft delete is forbidden — cancellations and refunds are expressed as new records. |
| Carts, CartLines | Hard-deleted after `expires_at` + grace period. |
| Customer, Customer PII fields | Soft-deleted on user request; PII fields scrubbed within the privacy SLA; biometric data deleted on consent withdrawal. |
| Products | Soft-deleted (`is_deleted = true`); references in historical orders remain. |
| Categories | Soft-deleted only if no active products reference them. |
| Inventory `StockMovement` | **Never** deleted (audit-grade). |
| Notifications | Hard-deleted after archive TTL (90 d) for in-app; sooner for transient channels. |
| Sessions | Hard-deleted on expiry / logout. |
| `DetectionResult` | Dropped with their partition (30 d). |
| `AIEvent` | Aggregated into Analytics, then dropped with their partition (90 d). |
| `AuditLog` | Never deleted within regulatory retention; archived after. |
| Snapshots | Per `purpose`: `incident` → linked retention; otherwise lifecycle-deleted. |

# Consistency Model

### Strong consistency (within a single aggregate)

- All invariants of a single aggregate are protected by an in-process
  **transaction** in the owning application service. Examples:
  - Cart total = sum of its lines + applied discounts.
  - Order paid → totals frozen, lines immutable.
  - Inventory: `quantity ≥ 0`, `reserved_quantity ≤ quantity`.

### Eventual consistency (across aggregates / contexts)

- Cross-context state changes are **driven by domain events**. They
  reach consumers within the EventBus latency window (sub-second in
  the in-memory implementation; broker-dependent later).
- Consumers are **idempotent** on `eventId` — re-delivery is safe.

### AI vs backend consistency model

- **AI proposes; backend decides.** AI events are *intent signals*,
  not authoritative state changes. The backend applies them through
  its own application services and enforces all invariants.
- A late, out-of-order, or duplicate AI event **MUST NOT** corrupt
  business state. The application service compares the event's
  `occurred_at` and `correlation_id` to existing state and is allowed
  to ignore stale signals.
- If the AI Engine is offline, AI-driven features are **silently
  degraded** (no smart cart updates, no queue alerts); manual flows
  continue to work and stay authoritative.

### Inventory consistency rules

- **Cart add → reserve, cart remove → release, order paid → commit,
  order cancelled → release** — all reservations / commits happen
  **inside the same Postgres transaction** as the cart/order change.
- **Idempotent payment**: the same `Idempotency-Key` on a retry
  produces the same Order, the same Payment row, and **no additional
  stock movement**.
- **No silent inventory change** — every change is paired with a
  `StockMovement` row (BR-12).
- **Stocktake variances** post as `ADJUSTMENT` movements; they cannot
  rewrite history.

### Multi-instance write consistency

- All writes go through the single Postgres primary; no multi-master
  writes in v1.
- Read replicas are **eventually consistent**; the application marks
  read-only paths and accepts replication lag for analytics / reports.

# Future Improvements

> Captured here for visibility; promoted into the roadmap or a new ADR
> when a real trigger appears.

### Storage & topology

- **Schema-per-tenant** for premium customers and regulated
  industries; the FK columns are already designed to make this a
  configuration choice rather than a rewrite.
- **Per-tenant sharding** for very large customers, hashed by
  `organization_id`.
- **Postgres logical replication** to a warehouse (BigQuery /
  Snowflake / DuckLake) for advanced analytics that exceeds the read
  replica's reach.

### Time-series & analytics

- **TimescaleDB extension** for hypertable management of
  `AIEvent`, `DetectionResult`, and analytics aggregates if the manual
  partitioning maintenance becomes a burden.
- **Materialised views** for frequently requested dashboard slices.
- **Columnar storage tier** (Parquet on S3) queried via DuckDB / Athena
  for ad-hoc analytics on cold data.

### Vector / AI

- **Postgres + pgvector** to host face / product embeddings alongside
  their metadata, removing the MinIO indirection for the recognition
  hot path.
- A dedicated **vector database** (Qdrant / Milvus / Weaviate) at very
  large scale; the application layer hides the choice.

### Performance

- **Optimistic concurrency** (`version` columns) on high-contention
  aggregates if measurement shows write conflicts.
- **Partial indexes** for "active only" predicates to shrink working
  sets.
- **Connection multiplexing** beyond PgBouncer (e.g. Odyssey) for
  Kubernetes deployments with many backend pods.

### Governance & compliance

- **Column-level encryption** for PII at rest (in addition to disk
  encryption).
- **Row-Level Security (RLS)** in Postgres as a *defence-in-depth*
  layer below the application's tenant predicate.
- **Audit object-lock** in S3 for tamper-evident long-term retention.
- **Right-to-be-forgotten tooling** as a managed pipeline that
  scrubs PII fields while preserving non-PII business records (orders,
  movements).

### Anti-goals (deliberately *not* on the plan)

- A NoSQL store as a second source of truth.
- Stored procedures or triggers carrying business logic.
- Storing binary data in Postgres `bytea`.
- Cross-tenant joins of any kind.

---

*This document is the canonical database design. Any change to entities,
relationships, partitioning, or consistency rules requires a PR that
updates **only this file** (and, when needed, an ADR explaining the
rationale).*
